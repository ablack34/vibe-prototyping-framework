# Template Reference

Document templates used throughout a VIBE engagement.

## Engagement Templates

These live in `templates/` and are populated as you progress through phases.

| Template | Created In | Purpose |
|----------|-----------|---------|
| `engagement-brief.md` | Preparation | **S42-internal brief** — commercial context, squad, success metrics, risks, sponsor map |
| `customer-brief.md` | Preparation | **Customer-voice brief** — the problem in the customer's own words, who feels it, what "great" looks like, existing investments, constraints |
| `PROJECT-CONTEXT.md` | Discover | Single source of truth — problem, personas, stakeholders, data, decisions (sections 3, 8 and 8.5 are short summaries that link out to the three Discover deliverables below) |
| `personas.md` | Discover | **Required Discover deliverable #1** — one persona per H2, sourced quotes, A/B/C grade per persona, sign-off block. Auto-generated by `/vibe-personas` into `engagement/<name>/personas.md` |
| `problem-statement.md` | Discover | **Required Discover deliverable #2** — formal "I am / I'm trying to / But / Because / which results in" with cited evidence per blank and customer sign-off. Auto-generated by `/vibe-problem-statement` into `engagement/<name>/problem-statement.md` |
| `current-state-journey.md` | Discover | **Required Discover deliverable #3** — Mermaid flowchart + stages table + Top 3 ranked pain points (feed the Disrupt workshop). Auto-generated by `/vibe-current-journey` into `engagement/<name>/current-state-journey.md` |
| `workshop-agenda.md` | Disrupt (pre-workshop) | Facilitator's run-of-show for the Week 2 workshop. Auto-generated by `/vibe-workshop-agenda` from the Discover deliverables + engagement brief. Anchors every section to a real persona / problem statement / OKR / pain |
| `workshop-record.md` | Disrupt (post-workshop) | What actually happened in the workshop — decisions, key quotes, parked items, action items, Discover edits surfaced. Auto-generated by `/vibe-workshop-record` from `sources/workshop/` |
| `future-state-journey.md` | Disrupt | Counterpart to `current-state-journey.md` — same persona, journey redesigned with the prototype in place. Top 3 improvements map 1:1 to the Top 3 current-state pains. Auto-generated by `/vibe-future-journey` |
| `storyboard.md` | Disrupt (flagship) | Scene-by-scene visual narrative (Setup → Challenge → Encounter → Solution → Impact). **The contract between Disrupt and Design & Develop** — engineer reads this to write the engineering brief. Auto-generated by `/vibe-storyboard` |
| `engineering-brief.md` | Design & Develop (scaffold) | **Engineer-written brief that becomes the squad-signed technical spec** — must-have / should-have / could-have features, integration points, build phases. Engineer copies `templates/engineering-brief.md` into `engagement/<name>/engineering-brief.md` as their first Design & Develop task and fills it from `storyboard.md` + `selected-concept.md` + `future-state-journey.md` |
| `solution-design.md` | Design & Develop | Internal technical document — architecture, tech stack, build phases |
| `CHECK-IN-NOTES.md` | Ongoing | Append-only log of customer check-in feedback and decisions |
| `PROTOTYPE-LIMITATIONS.md` | Deliver | Honest scoping of what the prototype does and doesn't do |

## What about a PRD?

The canonical VIBE PRD is **not a single document** — it's spread across six source files, each signed off by the right audience at the right time:

| # | Source file | Phase | Signed off by |
|---|-------------|-------|---------------|
| 1 | `problem-statement.md` | Discover | Customer |
| 2 | `personas.md` | Discover | Customer |
| 3 | `selected-concept.md` | Disrupt | Customer (live in the workshop) |
| 4 | `storyboard.md` | Disrupt | Customer (live in the workshop) |
| 5 | `future-state-journey.md` | Disrupt | Customer |
| 6 | `engineering-brief.md` | Design & Develop | Squad lead |

Keeping the PRD distributed across these six files means each artifact gets signed off in its natural phase by its natural audience — the customer isn't asked to review engineering minutiae, the squad isn't asked to re-litigate problem framing — and the canonical record can't drift out of sync with the work because each file *is* the record of the work that produced it.

### Need a single combined PRD?

When an engagement requires one polished document (governance gate, customer PMO, vendor onboarding), VIBE supports a **derived single-doc PRD** pattern. The six source files stay canonical — the combined PRD is generated from them, optionally validated by `@PRD Builder`, and any improvements get folded back into the source files rather than the combined doc.

```
SOURCE OF TRUTH                              DERIVED ARTIFACT
─────────────────────────                ─────────────────────────────
problem-statement.md     ─┐
personas.md              ─┤
selected-concept.md      ─┼─────────▶  prd.md (single combined PRD)
storyboard.md            ─┤                  ↑
future-state-journey.md  ─┤                  │
engineering-brief.md     ─┘            validated by (optional)
                                              │
                                       @PRD Builder
                                       (proposes improvements;
                                        only those that add real
                                        value are folded back to
                                        the source files and the
                                        PRD is regenerated)
```

**Design rule:** the combined PRD is a *derived artifact*. Never edit it directly. Edits land in one of the six source files and the combined PRD is regenerated. This is what stops the documents from drifting out of sync.

Generate the combined PRD with `/vibe-prd`. The structural template lives at `templates/prd.md`; the generated output lands at `engagement/<name>/prd.md` and embeds source SHAs so `/vibe-doctor` can warn if it's stale.

To also run a quality-review pass while generating, use `/vibe-prd validate=true` — this hands the generated PRD to `@PRD Builder`, which proposes improvements tagged by source file; accepted improvements are folded back into the appropriate source file and the PRD is regenerated.

`@PRD Builder` is documented in [the agents reference](agents.md).

## Tracking Artifacts

These are auto-generated in `engagement/{{engagement-name}}/` (committed) and `.copilot-tracking/vibe/{{engagement-name}}/` (per-user state):

| File | Created By | Purpose |
|------|-----------|---------|
| `state.json` | `/vibe-kickoff` | Engagement state, readiness tracking, phase progress |
| `transcript-analysis.md` | `/vibe-transcript` | Extracted requirements, decisions, pain points from meetings |
| `discovery-summary.md` | `@VIBE Discover` | Consolidated discovery findings |
| `ideation-concepts.md` | `/vibe-concepts` | 2-3 candidate concepts considered in the Disrupt workshop |
| `selected-concept.md` | `/vibe-selected-concept` | Chosen concept with detailed narrative (customer-signed in the workshop) |
| `spark-prompts.md` | `/vibe-concepts` | GitHub Spark and Copilot Studio prompts pasted into the workshop |
| `engineering-brief.md` | Engineer (first Design & Develop task) | Structured handoff the engineer writes from the storyboard |
| `prd.md` | `/vibe-prd` (optional) | **Derived combined PRD** — merges the six canonical source files into a single document. Only generated when a stakeholder requires it. |

## Source Materials

Drop these in `sources/`:

| Type | Examples |
|------|---------|
| Customer documents | Slide decks, RFPs, process diagrams |
| Questionnaire responses | Exported from Microsoft Forms |
| Workshop notes | Auto-created by `/vibe-capture` |
| Meeting schedule | `sources/meeting-templates.md` — full 4-week schedule (kickoff, 2× discover, disrupt workshop, 2× check-in, handoff), auto-created by `/vibe-kickoff` or `/vibe-schedule` |
| Customer research | `sources/research/customer-public.md` (Task Researcher, public web) and `sources/research/m365-researcher-results.md` (paste-back from M365 Copilot's Researcher), synthesised by `/vibe-research` into `sources/research/research-summary.md` |
